Fentaris can map API keys to users, load local encrypted credentials, and pass scoped credentials to upstream MCP servers.

## API Key Identity

`fentaris auth` shows incoming users and active key counts. `fentaris auth keys` offers an explicit action menu; specified commands work without redundant questions:

```bash theme={null}
fentaris auth keys create --user alice --name workstation
fentaris auth keys list --user alice --json
fentaris auth keys revoke <key-id> --non-interactive
```

Configure `identity: { strategy: projectVaultIdentityStrategy({root: process.cwd()}), required: true }` with your existing users/groups and access policy. Creation delivers the sensitive raw key once; only a verifier hash is persisted. Clients send `x-fentaris-api-key`. IDs and names are public metadata; expiry and revocation reject authentication. Knowing a credential reference never grants access.

## Upstream Authentication

Incoming users identify clients to Fentaris. Upstream account aliases identify the connection Fentaris uses to authenticate to an MCP server; aliases must not be inferred from incoming user/group scopes.

```ts theme={null}
mcp("linear", { transport: streamableHttp({ url: "https://mcp.linear.app/mcp" }), accounts: { work: { auth: oauth() } } })
```

Each named account has its own upstream authorization, stored through the project credential vault and refreshed automatically. Connect it with `fentaris mcp auth connect linear --account work`. Runtime selects the account with `upstreamAccounts` and still checks policy. Legacy per-user OAuth sessions require explicit migration and remain separate. The project vault's `oauthStore(account)` adapter isolates lifecycle-managed tokens by server, account, and session, keeping them outside manually editable inventory. See [Named MCP connections](/guides/mcp-connections) and [Upstream OAuth 2.1](/guides/oauth).

## Project Credentials

Use `credentialVault("github.work.token")` in the existing credential-source abstraction. `fentaris secrets set github.work.token` uses hidden input; scripts use `--stdin`. Get/list/check show sources, resolution state, and consumers without values. macOS Keychain stores the vault unlock key; CI/unsupported platforms require an explicit `FENTARIS_VAULT_KEY` or credential-store adapter. Fentaris never generates an unlock key into project `.env` or silently uses plaintext.

Environment/external sources are explicitly bound without copying values. Project `.env` loads before configuration; defined process values take precedence. Legacy `credentialJson` and `FENTARIS_AUTH_KEY` remain supported for recovery. Migrate with explicit mappings and retain the old data/key until verification. See [Project vault and client keys](/guides/project-vault).

## OAuth Resource Server

Use `oauthIdentityStrategy({ issuer, resource, scopes })` for inbound OAuth access tokens. Fentaris discovers the issuer's signing keys, validates token claims, and maps `sub` (or `mapUser`) to an existing user. Granted scopes appear in identity metadata; existing group policies still decide which MCP capabilities that user can access.

An ordered `identity` array accepts OAuth and API-key strategies together. The first successful strategy resolves the caller. HTTP and SSE listeners advertise protected resource metadata and add bearer discovery challenges to OAuth 401s. See [OAuth 2.1](/guides/oauth) for setup and introspection.
